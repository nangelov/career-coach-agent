## ⚠️ Key flag for the architect — pgvector cannot HNSW-index vector(4096)
The task/design assumed a plain `vector_cosine_ops` HNSW index on the 4096-dim embedding.
**That is impossible in pgvector:** HNSW/IVFFlat cap at **2000 dims for `vector`** and
**4000 for `halfvec`** (verified live — `CREATE INDEX ... vector_cosine_ops` fails with
*"column cannot have more than 2000 dimensions for hnsw index"*; halfvec fails at 4000). The
locked §6 decision fixes the dimension at **4096** and forbids truncation here.

I honored the lock (column stays `vector(4096)`) and used pgvector's **documented >4000-dim
pattern**: an HNSW index over the **binary quantization** of the embedding —
`USING hnsw ((binary_quantize(embedding)::bit(4096)) bit_hamming_ops)` (`bit` supports up to
64000 dims). The full-precision column is retained for **exact cosine** (`ORDER BY embedding
<=> :q`, which is the P2 exit-criterion query and the hybrid-search rerank). Net: the bit
index accelerates the ANN *candidate prefilter* (Hamming ≈ cosine on unit vectors); exact
cosine reranks. This is the "documented-alternative cosine-ops index" the acceptance criterion
allows. **If the architect prefers a different resolution** (Matryoshka-truncated 2000-dim
index, or accepting exact-scan-only), that's a §6/design ruling — flagging rather than
deciding it unilaterally.

  `source_type`/`memory_type` check constraints, document→chunk cascade, user→private-doc
  cascade (shared curated doc survives), and `source_message_id` SET NULL on message delete.

## Key decisions
- **Model layout follows P2-03:** one module per table group under `repositories/models/`,
  registered in `models/__init__.py`. `env.py` already imports the package for its metadata
  side effect (P2-03), so the new module is picked up automatically — confirmed via drift check.
- **`vector(4096)` kept, binary-quantize ANN index** — see the flag above.
- **`kb_chunks.content_tsv` = generated STORED tsvector** (`GENERATED ALWAYS AS
  to_tsvector('english', content) STORED`) via SQLAlchemy `Computed(persisted=True)`, with a
  **GIN** index — the lexical signal the P2-next hybrid-search task blends with vector
  similarity. Generated column (not a trigger) so it can never drift from `content` and needs
  no app writes. Autogenerate rendered this faithfully.
- **`metadata` JSONB → Python attribute named `meta`** (mapped to column `"metadata"`):
  `metadata` is a reserved attribute name on SQLAlchemy's declarative `Base`. Column name
  matches the design's `metadata JSONB`.
- **`kb_chunks.content` is NOT NULL** (a chunk is always text — it drives the tsvector) but
  **`kb_documents.content` is nullable** (the task's "large docs may prefer chunk-only
  storage; your call" — documented in the model: raw source blob optional, retrievable text
  lives in the chunks).
- **`source_type` / `memory_type` as `String` + `CheckConstraint`** (not native PG ENUM),
  matching P2-03's `role`/`rating` posture: adding a value later is a cheap check-constraint
  swap, not a fragile `ALTER TYPE`.
- **GDPR cascade (§4):** `kb_documents.user_id` and `user_memories.user_id` are
  `ON DELETE CASCADE` (private CV docs + learned memories are user-scoped, erased with the
  account); shared curated KB docs have `user_id` NULL and survive. `user_memories`
  `source_message_id` FKs the stable `messages.message_id` (§5.5) with **`ON DELETE SET
  NULL`** — pruning one message detaches the memory rather than destroying it (a user-delete
  still removes it via the `user_id` cascade).
- **HNSW over IVFFlat** (task preference): HNSW needs no training data, correct for tables that
  start empty — IVFFlat's `lists` centroids would be a no-op on an empty table.

## Notes for reviewers
- The one substantive deviation from the task wording is the **binary-quantize HNSW index**
  instead of `vector_cosine_ops` HNSW — forced by pgvector's 2000/4000-dim index cap vs the
  locked 4096 dim. Flagged above for an explicit architect ruling; exact cosine correctness is
  unaffected (it runs on the full-precision column, which the test proves).
- `env.py` now filters two functional indexes out of autogenerate (`_UNMODELED_INDEXES`). This
  is the standard pattern for expression indexes Alembic can't model; drift check confirms it
  keeps autogenerate quiet without hiding table/column changes.
- CI still doesn't run alembic or a live-DB test (same free-tier posture); the new test
  auto-skips without a reachable Postgres. `mypy` in CI targets `app/ migrations/`, covering
  the new model and `env.py` (`pgvector` is a declared dep; `ignore_missing_imports` handles
  its lack of stubs).
