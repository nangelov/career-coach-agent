## Notes
- Correctness verified: `stale_user_ids` groups by both non-aggregated columns (`User.id`, `User.created_at`), uses strict `<` (boundary user correctly excluded — proven in the live test), LEFT JOINs so never-chatted users still appear, and returns `str(uuid)` which `delete_user` re-parses via `uuid.UUID`. `created_at` columns are `DateTime(timezone=True)`, so the comparison against the tz-aware UTC cutoff is sound.
- Reuse of the SEC-05 `delete_user` cascade is exactly right — one cascading-delete path, no re-implementation. `from_provider`/`delete_user` signatures match. Best-effort loop catches per-user failures, logs with `exc_info`, and continues; each `delete_user` commits in its own session so a failure can't roll back prior successes. Task-level failure re-raises → Celery `FAILURE` → idempotent daily retry. Good.
- Only SSO users live in `users` (guests are Redis-only), so no guest/`is_admin` filtering is needed; uniform purge is the correct reading and is documented.
- Sessions caveat (informational, out of scope): like `DELETE /api/me`, the purge erases Postgres only and does not revoke a still-live Redis session record. A user purged while holding a login-refreshed (non-chat) Redis session would keep a bearer token pointing at a deleted `user_id` until TTL, and a subsequent chat turn would FK-violate. This is inherited from the reused `delete_user` primitive and explicitly out of this task's scope (`No change to DELETE /api/me beyond reusing delete_user`) — noting only, not gating. Ties to the session-registry-vs-Postgres enumeration pattern.
- beat wiring correct: daily `crontab(hour=3, minute=0)` entry targets `tasks.retention_purge`, task in `include`, new `beat` compose service mirrors `worker`. Config setting `RETENTION_PURGE_AFTER_DAYS` (default 30, not hard-coded) is threaded through. Unit tests (9) pass locally; coverage maps cleanly to acceptance criteria (cutoff math, all-stale, empty no-op, one-failure-continues, wall-clock default, registration+beat) plus live-DB boundary/fallback + full-footprint cascade vs fresh survival.
