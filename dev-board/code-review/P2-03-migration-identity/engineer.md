# Engineer report — P2-03-migration-identity · Revision 1

## Summary
Landed the **first real v2 migration** (`0002`) on top of P2-02's `0001` baseline, plus the
SQLAlchemy 2.x ORM models it derives from, covering the **identity / conversation / documents**
table group (design §4): `users`, `profiles`, `preferences`, `sessions`, `conversations`,
`messages`, `message_feedback`, `feedback` (8 tables). Schema-only — no persistence wiring, no
endpoints. Models subclass the shared `Base` from `app/repositories/postgres.py`; the migration was
`--autogenerate`d then hand-reviewed (renumbered to sequential `0002`, DDL verified against the
models). Verified **live against the docker-compose Postgres**: `upgrade head` → `downgrade 0001` →
`upgrade head` all clean, autogenerate reports **no drift**, and an insert/read-back integration test
exercises every table plus the unique/check/cascade constraints. `ruff` + `mypy --strict` clean; full
suite 89 passed.

## Files changed
- `backend/app/repositories/models/__init__.py` — **new.** Model subpackage; imports every model
  module so `Base.metadata` is fully populated by a single `import app.repositories.models`. Exports the
  8 model classes.
- `backend/app/repositories/models/identity.py` — **new.** The 8 ORM models (SQLAlchemy 2.x
  `Mapped`/`mapped_column`), JSONB via `postgresql.JSONB`, `postgresql.UUID` PKs, FKs with explicit
  `ondelete`, unique/check constraints, FK indexes, relationships with cascade.
- `backend/migrations/versions/20260705_0002_identity_and_docs.py` — **new.** The migration
  (`revision="0002"`, `down_revision="0001"`). Autogenerated then hand-edited (renumbered, documented,
  reformatted to house style).
- `backend/migrations/env.py` — added a side-effecting `import app.repositories.models` so
  `--autogenerate` sees the models on `Base.metadata` (without it, autogenerate would propose dropping
  everything). ruff reordered the import; comment preserved.
- `backend/tests/test_identity_models.py` — **new.** Real-Postgres integration test (skips when no DB
  reachable): insert-and-read-back across all 8 tables, `(provider, sub)` uniqueness, `message_id`
  uniqueness, `role` check constraint, user-delete cascade, and product-`feedback` SET NULL survival.
- `backend/tests/test_postgres_repository.py` — updated the stale P2-01 assertion
  `Base.metadata.tables == {}` (true only before any models existed) to assert the identity group is now
  registered on the shared metadata. Necessary because importing the models populates the process-wide
  `Base.metadata`.

## Key decisions
- **Model layout: a `repositories/models/` subpackage, one module per table group** (`identity.py` now;
  `knowledge.py`/`dashboard.py` follow in P2-04/05). Keeps models in the repository layer (§4/§8), scales
  cleanly, and gives `env.py`/tests a single import to populate metadata. P2-04/05 should add a module +
  an import line in `models/__init__.py`.
- **`sessions.id` is a `String(64)` PK, not a DB UUID.** The id is minted client-side
  (`crypto.randomUUID()`, P1-08) and arrives as `session_id: str` on `ChatRequest` — the schema stores the
  app's existing shape without forcing a type change (task requirement).
- **`messages.message_id` is a `String(32)`, unique, app-side default `uuid4().hex`** — matches
  `ChatService`'s minted id (§5.5). `message_feedback.message_id` FKs to it (the natural key), not to the
  surrogate `id` PK, so the P9 feedback endpoint keys on the same id the stream emitted. Each message row
  also has a surrogate `UUID` PK.
- **`role` / `rating` as `String` + `CheckConstraint`** rather than native PG `ENUM`: roles stay in
  lockstep with `app.llm.types.Role` and adding a value later is a cheap check-constraint swap, not a
  fragile `ALTER TYPE` migration.
- **GDPR cascade posture (§4):** user-delete cascades to profile / preferences / sessions / conversations
  / messages / message_feedback. **Product `feedback` is the deliberate exception** — its `user_id` /
  `session_id` FKs are `ON DELETE SET NULL` so product feedback (and its analytics value) **outlives** the
  account, as the task explicitly allowed. Documented in the model + migration docstrings.
- **JSONB (not JSON)** for `users.settings`, `profiles.data`, `preferences.data`, `messages.trace` (§4).
- **`profiles.user_id` / `preferences.user_id` are `unique`** — enforces "one per user" (§4/§5.4).
- **Migration renumbered `0002`** (from the autogenerate hash) to match the `0001` baseline's clean
  sequential chain; DDL is otherwise the verified autogenerate output.
- **`email` is `NOT NULL`** — login requests the `email` scope (§7.1); indexed for support lookups, not
  unique (one person may sign in via two providers). No password column anywhere (§7.1 hard constraint).

## How to verify
From `backend/` with the app env set (host DSN → running db container):
```bash
set -a && . ../.env && set +a
export DATABASE_URL="postgresql+asyncpg://${POSTGRES_USER}:${POSTGRES_PASSWORD}@localhost:5432/${POSTGRES_DB}"

alembic upgrade head          # 0001 -> 0002
alembic revision --autogenerate -m "drift check"   # body is empty `pass` → no drift (delete the file)
alembic downgrade 0001        # drops all 8 tables cleanly
alembic upgrade head          # back to 0002

pytest tests/test_identity_models.py -q   # 6 passed (skips if no DB reachable)
ruff check . && ruff format --check .     # All checks passed! / 52 files already formatted
mypy app/ migrations/                     # Success: no issues found in 37 source files
pytest -q                                 # 89 passed
```
**Actually run here (live docker-compose Postgres, pgvector/pg16 on :5432):**
- `upgrade head` applied `0002`; `alembic current` → `0002 (head)`.
- `--autogenerate` drift check → empty `upgrade()` (`pass`) → models and migration match exactly.
- `downgrade 0001` → all 8 identity tables gone (`information_schema` count = 0); `upgrade head` reapplied.
- Integration test: insert one row per table with valid FKs + read back (JSONB round-trips), `(provider,
  sub)` and `message_id` uniqueness raise `IntegrityError`, out-of-vocab `role` rejected by the check
  constraint, user-delete cascades to owned rows, product `feedback.user_id` goes NULL on user-delete.
- `ruff`/`ruff format`/`mypy --strict` clean; full suite **89 passed**.
