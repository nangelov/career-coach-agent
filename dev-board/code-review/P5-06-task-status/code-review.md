## Notes
- **AuthZ decision is acceptable, not a gate.** `task.md` explicitly stated "either is defensible; pick one, justify it briefly," and required only that (a) auth is required and (b) the guest CV flow isn't blocked. Both hold. The `task_id` is a 122-bit UUID4 handed back only to the enqueuing request, `require_auth` blocks anonymous scanning (401 verified), the failure path returns a generic message with the exception object dropped (no PII/traceback leak — asserted by tests), and the guest preview flow depends on the poll result being readable. This is a textbook capability-URL pattern and a reasonable KISS/YAGNI call for P5. C1/C2 refine the *rationale* and flag *residual* risk; neither is a defect that blocks the task. The system-architect owns the final call on whether the capability model conforms to the §7 "users access only their own data" posture.
- **Correctness is solid.** `map_async_result` is pure and total over Celery's state set; `FAILURE`/`REVOKED` return early before any exception object could surface; the `isinstance(info, dict)` guards on both the success payload and the progress-meta path prevent an exception object (e.g. on `RETRY`, whose `.result` is the exception) from leaking into `stage`/`message`/`result`. `state`/`stage`/`message` only ever carry static, producer-defined strings.
- **Layering / testability are clean.** Thin router (auth + `asyncio.to_thread` offload of the blocking result-backend read) → pure service, with the only Celery seam behind an injected `AsyncResultFactory` Protocol. Unit tests exercise the mapping against the *real* producer's state names/meta/result shape (imported from `app.tasks.profile_ingest`), proving no producer rework — good practice. Blocking Redis I/O correctly kept off the event loop.
- **Lazy DI (`get_job_status_service`) check-then-set race is benign here** — `JobStatusService` holds no pooled resource (the factory opens no connection at construction), so a concurrent double-build is harmless and matches the established composition-root convention.
- Verified locally: `ruff check` clean, `mypy` clean on the 3 changed source files, and `pytest tests/test_jobs_api.py tests/test_job_status_service.py` → 16 passed. Pre-existing mypy noise in unrelated files is correctly out of scope.
