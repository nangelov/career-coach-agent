## Findings
| id | severity | file:line | issue | required change |
|----|----------|-----------|-------|-----------------|
| C1 | minor | app/repositories/redis.py:152-162 | `append` issues `rpush` → `ltrim` → `expire` as three separate round-trips, not a pipeline/`MULTI`. Two concurrent appends to the same `session_id` can interleave, and if the process dies (or `expire` errors) after `rpush` but before `expire`, the session list persists with **no TTL** until the next successful append refreshes it — a leaked unbounded key. | For P2, wrap the three commands in a `pipeline(transaction=True)` (or a small Lua script) so append is atomic and the TTL can never be dropped. Acceptable to defer for the P1 skeleton; note it so it isn't lost. |
| C2 | minor | app/api/chat.py:49-72, 75-85 | Lazy DI on `app.state` without a lock: concurrent first requests each run `build_chat_service`, each constructing a **new** `RedisConnectionProvider` (a new `ConnectionPool`). Only the last write to `app.state.redis_provider` is closed on shutdown → earlier pools leak. Same class of race as the P1-04 service cache. | Interim-acceptable and already earmarked for P2 shared-pool wiring; guard the build (lock/eager init at lifespan startup) when composition moves in P2. |
| C3 | minor | app/services/chat.py:155,176-202 · app/repositories/redis.py:152 | Client-supplied `history` seeds the model turn *instead of* `memory.load`, but the turn's produced messages are still `RPUSH`'d onto the existing Redis list. If Redis already holds prior turns for that `session_id`, the stored history diverges from what the model actually saw and can accumulate stale/duplicated context. Matches the P1-04 `ChatRequest.history` trust note (also lets a client inject `system`/`tool` roles). | Not this task's scope (documented, deferred to the P3 auth trust boundary). Carry the divergence + role-restriction into P3/P10; don't gate here. |
| C4 | minor | app/repositories/redis.py:115-119,152-162 | Documented count-cap can split an assistant `tool_calls` / `role="tool"` pair at the boundary for a conversation longer than `SESSION_MEMORY_MAX_MESSAGES` (default 100). The next `load` then returns an orphan `tool` message, and the OpenAI-compatible API rejects it (400) → a terminal `error` event that recurs until the orphan ages out — a session that stays broken. | Behavior is explicitly documented (docstring + engineer.md) and matches the interim store; a turn-aware cap is the deferred fix. Acceptable for P1 as a walking-skeleton limitation — note only. |
