## Notes
- **Acceptance criteria: all met and test-pinned.** id generated exactly once (`message_id = uuid4().hex` at the single top-of-`stream_turn` point, `chat.py:187`) and reused for `start`/`done`/`cancelled` and the persisted answer; identical across a plain turn and a multi-iteration tool turn; distinct across turns and sessions (uuid4); survives both the in-memory and the Redis `model_dump_json → model_validate_json` round trip; cancelled partial keeps the streamed id (`chat.py:223-230`); excluded from the provider payload (`to_openai()` whitelists `role`/`content`/`name`/`tool_calls`/`tool_call_id` — `types.py:66-95`) with two regression tests. Verified locally: `ruff check` clean, `ruff format --check` clean, `mypy app/` clean (31 files), `pytest -q` 71 passed (9 new).
- **Single generation point confirmed** — grepped: `uuid4().hex` for the turn id occurs only at `chat.py:187`; never regenerated inside the token/tool loop. The other `uuid4().hex` (`chat.py:90`, `_ToolCallAccumulator.to_tool_call`) is an unrelated fallback tool-call id.
- **No SSE frame injection** — `_format_sse` JSON-encodes the payload via `json.dumps` (`api/chat.py:99-102`); `message_id` reaches the wire through `model_dump(exclude={"event"})`, not raw interpolation.
- **Client-supplied `message_id` is harmless.** `ChatRequest.history` items can now carry a client `message_id`, but supplied history is used to seed the model call only and is **not** appended to `turn.produced`/session memory (`chat.py:188-196, 241`), so it can never be returned by `get_message` (which scans server-stored history) and is dropped at `to_openai()` regardless. The broader "constrain accepted client history roles" trust-boundary item remains the pre-existing P1-05 → P3 concern, untouched here (correctly out of scope).
- **Uniqueness of `get_message` results holds** — one stamped message per turn, ids unique per turn, so the first-match scan resolves to exactly one message.
- **Iteration-cap and cancel-between-tool-calls paths** correctly emit no user-facing stamped answer (nothing the user reacted to); documented and consistent with the acceptance criteria scope.
- **Design-conformance judgment deferred to system-architect:** stamping only the terminal user-facing assistant message (not intermediate tool-request assistant messages) is the engineer's reading of §5.5 "each assistant message carries a stable `message_id`". The 1:1 feedback-handle rationale is sound for correctness; whether it matches the design intent is the architect's call.
