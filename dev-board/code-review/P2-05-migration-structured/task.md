# Task P2-05-migration-structured — Migration: structured records (jobs, pdps, dashboard)
- **Phase:** P2   **Status:** ENG   **Tags:** (B)

## Scope
Add the **third real Alembic migration**, on top of P2-04's knowledge/vectors migration, covering the
**structured records** table group (design §4 "structured records" + §5.2 "Dashboard — the living PDP").
Follow the `repositories/models/` subpackage convention from P2-03/P2-04 (new module(s), e.g.
`models/jobs.py` + `models/dashboard.py`, or one `models/structured.py` — your call, document it;
registered in `models/__init__.py`).

Tables:
- `jobs` — normalized job listings + crawled role profiles (§4: "dedup, cache, match scores"): id,
  `external_id`/`source_url` (unique-ish key for dedup — document your dedup key choice), `title`,
  `company`, `location`, `description` text, `raw JSONB` (original crawled/source payload, for
  re-processing without re-crawling), `match_score` (nullable float — computed per-user later, so if a
  match score is inherently per-user rather than global, consider whether it belongs on `jobs` at all or on
  a join table; document your reasoning either way — a simple global `jobs` table with match-scoring
  deferred to a later feature is an acceptable, documented simplification for this schema-only task),
  `fetched_at`/`created_at`, `updated_at`.
- `pdps` — generated PDP records (§4: "PDF stored in object storage or regenerated on demand" — no object
  storage exists yet, so store enough to regenerate: `user_id` FK, `career_goal`, `target_date`,
  `content JSONB` or the structured markdown sections v1 generated, `pdf_path`/`pdf_url` (nullable — future
  object-storage pointer), `created_at`).
- `goals` — user career goals (§5.2): id, `user_id` FK (cascade-delete), `title`, `target_role`,
  `target_date`, `status` (checked varchar, e.g. `active`|`completed`|`abandoned`), `created_at`,
  `updated_at`.
- `milestones` — checkpoints under a goal: id, `goal_id` FK (cascade-delete), `title`, `due_date`,
  `status`, `created_at`, `updated_at`.
- `tasks` — actionable items (§5.2 — note this is the **dashboard** `tasks` table, unrelated to Celery
  tasks in `app/tasks/`; name the ORM class to avoid ambiguity, e.g. `DashboardTask`, and document the
  naming choice so it isn't confused with Celery task modules): id, `goal_id` FK **and/or** `milestone_id`
  FK (§5.2 lists tasks under milestones under goals — decide whether `tasks.milestone_id` is required or
  optional-with-a-direct-`goal_id`-fallback for "no milestone yet" tasks; document your call), `title`,
  `description`, `due_date`, `status`, **`source`** (checked varchar `user`|`ai` — §5.2: *"every change is
  attributable (source = user|ai)"*), `created_at`, `updated_at`.
- `progress_entries` — append-only log (§5.2: "trend/streak views"): id, `user_id` FK, optional `goal_id`/
  `task_id` FK, `note` text, `created_at` (no `updated_at` — append-only, do not add an update path).

## Design note: AI-write safety posture (§5.2)
§5.2 states AI writes to the dashboard must be **"explicit, confirmable changes (proposed → user
approves) rather than silent mutations."** This task is schema-only (no agent/tool code yet — that's a
later phase), but the schema should not preclude that workflow: ensure `source` (`user`|`ai`) is present
wherever attribution matters (`tasks` at minimum; consider `goals`/`milestones` too) so a future
"proposed-by-ai, pending approval" status value fits into the existing `status` check constraint without
another migration. Document this consideration in `engineer.md` even if you don't add a dedicated
`approved_at`/`proposed` column yet (that can be a later, feature-scoped migration).

## Build
- ORM models subclassing the shared `Base`, cascades (`user_id`/`goal_id`/etc. FKs cascade-delete per the
  established GDPR posture from P2-03/04), checked-varchar status/source columns (matching the
  `role`/`rating`/`memory_type` pattern from prior migrations, not native Postgres `ENUM`, for the same
  cheap-to-extend reasoning already documented in P2-03's engineer report).
- Alembic migration, `down_revision` = P2-04's revision, autogenerated then hand-reviewed.
- No pgvector columns in this group (jobs/PDPs/dashboard are plain relational + JSONB, per §4).

## Verification
- Live-Postgres verification: `alembic upgrade head` / `downgrade` back to P2-04's revision, both clean.
- Insert-and-read-back integration test covering all 6 tables plus at least one cascade-delete assertion
  (deleting a `goals` row removes its `milestones`/`tasks`; deleting a `users` row removes their
  `goals`/`pdps`/`progress_entries`, consistent with prior migrations' GDPR cascade tests).
- `ruff` + `mypy` clean.

## Constraints / non-goals
- No agent/tool code that actually writes to these tables (no dashboard tools, no PDP-generation endpoint
  rewrite) — that's later phases. This task is schema-only, same posture as P2-03/04.
- No object storage wiring for `pdps.pdf_path` — just the column, nullable, for a future integration.
- No Celery task changes — `tasks` here is the dashboard table, not `app/tasks/` Celery modules; keep them
  clearly distinguished (naming, not the same namespace).
