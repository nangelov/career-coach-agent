**structured records** table group (design §4 "structured records" + §5.2 "Dashboard — the

## Key decisions
- **Module split (documented per task):** two modules — `jobs.py` (`Job`) and `dashboard.py`
  (`Pdp` + the goal/milestone/task/progress hierarchy). `pdps` lives in `dashboard.py` because
  the PDP generator *"seeds the dashboard's goals/tasks"* (§5) — it is part of the living-PDP
  story, not the job-search story. Kept `jobs` separate as it shares nothing with the rest.
- **`jobs` dedup key = `UniqueConstraint(source, external_id)`** (documented choice). Chosen
  over `source_url` because listing URLs redirect, carry tracking params, and differ across
  aggregators for the same role; a provider's own `(origin, id)` pair is the stable natural
  key. Crawled role profiles with no provider id get a synthetic `(source='crawl',
  external_id=<hash of canonical URL>)` from the ingestion layer (app-layer concern), so every
  row has a key. `source_url` is kept nullable + **non-unique** (indexed) as reference/re-crawl
  metadata. `raw JSONB` retains the source payload for re-parsing without re-crawling (§4).
- **`jobs.match_score` = nullable global placeholder; per-user matching deferred.** A real
  job↔profile match is inherently **per-user**, so it does not belong on a globally-shared
  `jobs` row. Per the task's explicitly-accepted simplification, the global column stays
  nullable (may hold an optional source-provided relevance score) and true per-user scoring is
  deferred to a future `user_job_matches` join table (`user_id` + `job_id` + `score`, cascading
  `user_id`). `jobs` therefore has **no `user_id`** and is untouched by a GDPR user-delete
  (it's a shared cache, unlike P2-04's private CV docs).
- **AI-write safety posture (§5.2) baked into the schema, schema-only.** No dashboard
  tools/agent code (later phase), but the schema must not preclude "proposed → user approves":
  (1) **every mutable dashboard entity** (`goals`, `milestones`, `tasks`, `progress_entries`)
  has a checked `source` (`user`|`ai`) column for attribution — the task required it on `tasks`
  at minimum and invited it on `goals`/`milestones`; I added it to all four (including the
  append-only log, whose entries can be user- or AI-authored) for uniform attribution. (2)
  Each `status` check vocabulary **already includes `'proposed'`** — the pending-approval state
  an AI-proposed row starts in — so introducing that workflow needs no schema migration. A
  dedicated `approved_at`/`proposed_by` column, if ever wanted, is left to a later
  feature-scoped migration (as the task allows).
- **`tasks` anchoring (documented choice):** every task requires a `goal_id` (NOT NULL,
  cascade) and *optionally* a `milestone_id` (nullable). This supports "no milestone yet" tasks
  directly under a goal. Deleting a milestone **`SET NULL`s** its tasks' `milestone_id` (they
  survive, falling back to the goal) rather than deleting them; deleting the goal removes the
  tasks via the `goal_id` cascade. Verified live in `pg_constraint`.
- **Naming: `DashboardTask` ORM class → table `tasks`.** Deliberately named `DashboardTask` to
  stay **unambiguously distinct** from the Celery task modules in `app/tasks/` (`celery_app.py`,
  `ping.py`) — this is a persisted dashboard row, not a background job. Different namespace,
  documented in the class docstring.
- **`progress_entries` is append-only:** no `updated_at` column and no update path modeled —
  the log *is* the history (§5.2 trend/streak views). Its `goal_id`/`task_id` are `SET NULL`
  (not cascade) so the log survives the user editing/deleting the plan it refers to; only a
  user-delete erases it (via the `user_id` cascade).
- **Checked varchar, not native ENUM** for all `status`/`source` columns — matching the
  `role`/`rating`/`memory_type`/`source_type` posture from P2-03/04: extending a vocabulary is
  a cheap check-constraint swap, not a fragile `ALTER TYPE` (the exact reasoning documented in
  P2-03's report).
- **GDPR cascade (§4):** user-delete cascades to `pdps`, `goals` (→ `milestones` → `tasks`)
  and `progress_entries`; deleting a goal cascades to its milestones and tasks. All confirmed
  in `pg_constraint` (see "How to verify").
- **No `env.py` change needed** (unlike P2-04): this group has no functional/expression indexes
  to exclude from autogenerate — the empty drift-check `upgrade()` confirms it.

## How to verify
From `backend/` with the app env set (host DSN → running `db` container on :5432):
```bash
set -a && . ../.env && set +a
export DATABASE_URL="postgresql+asyncpg://${POSTGRES_USER}:${POSTGRES_PASSWORD}@localhost:5432/${POSTGRES_DB}"

alembic upgrade head                            # 0003 -> 0004
alembic revision --autogenerate -m "drift"      # upgrade() body empty → no drift (delete file)
alembic downgrade 0003                           # drops the 6 tables cleanly
alembic upgrade head                             # back to 0004

pytest tests/test_structured_models.py -q        # 10 passed (skips if no DB reachable)
ruff check . && ruff format --check .            # All checks passed! / already formatted
mypy app/ migrations/                            # Success: no issues found in 42 source files
pytest -q                                        # 108 passed
```
**Actually run here (live docker-compose Postgres on :5432):**
- `upgrade head` applied `0004`; `alembic current` → `0004 (head)`.
- `--autogenerate` drift check → empty `upgrade()` (no `op.*` calls) → deleted.
- `downgrade 0003` → `information_schema` count of the 6 tables = **0**; `upgrade head` →
  count = **6**.
- FK on-delete rules confirmed via `pg_constraint`: `pdps.user_id`/`goals.user_id`/
  `milestones.goal_id`/`tasks.goal_id`/`progress_entries.user_id` = **CASCADE**;
  `tasks.milestone_id`/`progress_entries.goal_id`/`progress_entries.task_id` = **SET NULL**.
- `tests/test_structured_models.py` → **10 passed** (incl. goal→milestone→task cascade,
  milestone-delete-detaches-task, user→goals cascade, progress-entry survives goal-delete but
  not user-delete, dedup uniqueness, status/source check constraints).
- `ruff`/`ruff format`/`mypy --strict` clean; full suite **108 passed**.

## Notes for reviewers
- **Dedup key** and **per-user match-score deferral** are documented judgment calls the task
  explicitly asked me to make and justify — see "Key decisions". If the architect prefers
  `source_url` as the dedup key or wants the `user_job_matches` join table now, that's a
  scope/design ruling I'm flagging rather than pre-empting.
- **`source` on all four dashboard entities** (not only `tasks`) is a deliberate superset of
  the task's minimum ("`tasks` at minimum; consider `goals`/`milestones` too") for uniform
  §5.2 attribution — including the append-only `progress_entries`, since a progress note can be
  AI-authored.
- **`'proposed'` in every status vocabulary** is the concrete way I honored the task's
  "future proposed-by-ai status fits the existing check constraint without another migration"
  requirement — added now so the P-later dashboard-tools phase needs no schema change.
- The container image (`career-coach-agent-backend-1`) predates the `migrations/` tree, so
  alembic was run from the **host venv** against the live DB (same approach P2-04 used); the
  host venv has `asyncpg`/`pgvector`/`sqlalchemy`. CI still doesn't run alembic or a live-DB
  test (free-tier posture); the new test auto-skips without a reachable Postgres. `mypy` in CI
  targets `app/ migrations/`, covering both new model modules and the migration.
